Walgreens storefront · Prototype

Server-rendered nav at the edge

A prototype that delivers the Walgreens site navigation as a server-rendered React app, running on Adobe App Builder and placed into the Edge Delivery Services (EDS) page by an AEM Edge Function. With the edge function, the nav is already in the first HTML response, so the browser shows it without a separate request. The prototype reads the nav content from the authored EDS /nav document, but the same model works with any content source (see Content source).

Terms used below: the nav app returns an HTML fragment, a piece of HTML for the page's <header> rather than a full page. In the browser, React then hydrates it, attaching its event handlers to that existing HTML so the menus work. Stage is the App Builder test workspace; Production isn't deployed yet.

What's needed for production

  • Licensing and environments: Adobe App Builder; a Cloud Manager program with the Edge Delivery Services add-on and AEM Edge Functions; a custom domain on the Adobe-managed CDN.
  • A CDN topology decision: where the nav is inserted when Akamai serves the site (see Running behind Akamai).
  • A Production deployment of the nav app (only Stage is deployed today) and of the edge function.
  • Resilience: a fallback for when App Builder is unavailable, since the nav app is currently required.
  • Commerce features in the nav (live search, signed-in account state, mini-cart), which the prototype doesn't include.
  • The real content source, mapped into the nav model (see Content source).
  • Variants by audience (locale, store, signed-in state), if needed. The prototype serves one nav to everyone.

How the nav is delivered

The same React nav is used on every page. What differs is when it reaches the browser.

With the edge function

  1. A visitor requests a page on the site's domain.
  2. The edge function fetches the page from EDS and the nav HTML from App Builder (cached for 5 minutes).
  3. It puts the nav into <header> and returns one HTML response.
  4. The browser shows the nav immediately; the React bundle then makes the menus interactive.

In the page source, <header> already contains id="wnav-root". The response header X-Edge-Nav: stitched means the edge function inserted the nav; X-Edge-Nav: fallback-… means it returned the page unchanged.

Without the edge function

  1. The page arrives from EDS with an empty <header>.
  2. The EDS header block fetches the same nav HTML from App Builder in the browser.
  3. It loads the nav's stylesheet, inserts the markup, and the React bundle makes it interactive.

This is what aem.page and aem.live URLs show, and what the edge function falls back to if the nav is slow or its request fails. In DevTools → Network you'll see a separate nav-app/nav request after the page loads.

Using a different content source

In this prototype the nav content comes from the EDS /nav document, because that's where this site's nav is authored today. Your nav can come from anywhere else instead. The nav app works in two stages, and only the first one knows where the content lives:

1 · Read the content and build the nav model

Fetches the content and converts it into a plain JSON nav model (shape below).

This is the part you replace. Today it fetches /nav.plain.html and parses it: fetchModel in nav-app/actions/nav/index.js, using nav-app/src/parse-nav.js.

2 · Everything after the model

React renders the model to HTML, the response is cached, the edge function or the EDS header block puts it in the page, and the browser hydrates it.

This stays the same, whatever the source.

The source could be a headless CMS, AEM Content Fragments through GraphQL, a commerce category tree, a navigation service, or a JSON file. Map it into this shape and the rest of the solution is unchanged: 

{
  "promo":   [{ "label": "Earn $10 in rewards* …", "href": "/offers/offers" }],
  "brand":   { "href": "/", "alt": "Walgreens: Trusted since 1901", "src": "https://…/logo.svg", "sources": [] },
  "search":  { "label": "Search", "action": "/search" },
  "store":   "151 N State St, Chicago, IL",
  "account": { "label": "Account", "links": [{ "label": "Sign in", "href": "/customer/login" }] },
  "nav": [
    { "label": "Pharmacy", "children": [
        { "label": "Prescriptions", "children": [
            { "label": "Refills", "href": "https://www.walgreens.com/pharmacy/…" } ] } ] },
    { "label": "Weekly Ad", "href": "/offers/offers-jsp/weeklyad" }
  ],
  "cart":    { "label": "View shopping cart", "href": "/cart" }
}

nav is a tree. An item with children opens a menu; inside a menu, an item with its own children is a group, an item with href is a link, and an item with neither is a heading. ?format=json on the Stage nav app returns the full current model.

What to plan for with another source

  • Mapping: replace fetchModel with a call to the new source and a mapping into the model. The model is the contract, so the mapping is the only new code.
  • Credentials: if the source needs an API key or token, pass it to the action as an App Builder input from a secret (declared in app.config.yaml). It stays on the server and never reaches the browser.
  • Freshness: the nav HTML is cached for 5 minutes. If the source can notify on publish, the cache lifetime can be raised and purged on change instead.
  • Sources that differ by audience (for example locale, store or signed-in state) need that dimension in the fragment URL, and in the edge function's cache key, so visitors don't share the wrong nav.

Run it locally

You can run the site on its own (the nav is loaded in the browser), or with the edge function in front of it (the nav arrives inside the page). Both use the nav app already deployed on App Builder Stage, so no Adobe account is needed.

Prerequisites

  • Node.js 22 or later, and Git
  • For the edge function only: the Fastly CLI, which runs Fastly Compute locally. On macOS: brew install fastly/tap/fastly
git clone https://github.com/AdobeDrago/walgreens-storefront.git
cd walgreens-storefront

Option 1 · EDS only

Start the EDS development server from the repository root:

npx -y @adobe/aem-cli up --no-open

Open http://localhost:3000/. Code comes from your working copy; page content comes from the EDS preview site, https://main--walgreens-storefront--adobedrago.aem.page. The header block fetches the nav from the App Builder Stage nav app in the browser.

Option 2 · EDS + edge function

Keep Option 1 running. In a second terminal:

cd edge-nav
npm install
npm run local

Open http://127.0.0.1:7676/. npm run local compiles the edge function to WebAssembly and runs it with the Fastly CLI in front of localhost:3000, so every page comes back with the nav already in <header>.

Telling them apart

CheckEDS only (:3000)EDS + edge function (:7676)

On both, the nav is the React app: the Nav component appears in the React Developer Tools extension.

Optional · run the nav app locally too

To change the nav itself, run the nav app too. In a third terminal, from the repository root:

cd nav-app
npm install
npm run dev                      # http://localhost:3100/  (the nav on its own)

Then, in the edge-nav terminal, stop npm run local (Ctrl+C) and restart it pointed at the local nav app:

NAV_FRAGMENT_URL=http://localhost:3100/fragment npm run local

npm run local also accepts EDS_ORIGIN (default http://localhost:3000) and EDGE_PORT (default 7676). Option 1's header block always uses the Stage nav app.

Architecture

The fragment the nav app returns is one self-contained piece of HTML:

<link rel="stylesheet" href="…/web-src.<hash>.css"> <div id="wnav-root"> …server-rendered nav… </div> <script type="application/json" id="wnav-data"> …nav model… </script> <script src="…/web-src.<hash>.js" defer></script>

Endpoints (Stage)

Base URL: https://4191536-703coralcanid-stage.adobeio-static.net/api/v1/web/nav-app/nav

URLReturns
(base URL)The HTML fragment
(base URL)?format=pageThe nav on a page of its own

Responses are cached for 5 minutes (Cache-Control: public, max-age=300, stale-while-revalidate=600) and allow cross-origin requests.

Design decisions

DecisionReason
AEM Edge Functions to insert the nav into the pageKeeps the solution on Adobe's stack. Edge functions run on Fastly Compute inside the Adobe-managed CDN in front of EDS, and are routed per path with cdn.yaml.
App Builder for the nav appOne Adobe project hosts both the server render (an I/O Runtime web action) and the browser bundle (static hosting on Adobe's CDN).
React server rendering rather than Next.jsI/O Runtime actions are short-lived functions, while Next.js expects its own long-running server and has no supported adapter. React's renderToString plus hydrateRoot demonstrates the same render-on-server, hydrate-in-browser pattern without that overhead.
The prototype reads the authored /nav documentAuthoring doesn't change for this site, and the parser follows the same section order the EDS header always used. The source can be replaced without touching the rest (see Content source).
Same markup and styles as the existing EDS headerThe React component renders the same structure and classes as the site's previous header, so the nav matches it in the layouts and interactions tested (see Verification).
No build step for the componentThe component uses htm templates instead of JSX, so one file runs on the server, in tests and in the browser bundle.
The browser bundle is a classic deferred scriptIt loads from App Builder's domain, which doesn't send CORS headers; classic scripts don't need them, while module scripts do.
A slow nav doesn't hold up the pageIf the nav takes more than 1.5 seconds, or its request fails, the edge function returns the page unchanged and the header block retries in the browser. If App Builder itself is down, neither path can show a nav (see Considerations).

Considerations

Adobe notes that server-side or edge HTML assembly is not required for Edge Delivery Services, which already delivers fast pages with client-side blocks. This prototype demonstrates the pattern for teams that want a component like the nav rendered as a separate app; weigh the extra moving parts against that.
  • Commerce features in the nav are not wired yet. Live search results, signed-in account state and the mini-cart with item count aren't part of the React nav. Search submits to /search?q=, the account menu always shows "Sign in", and the cart is a link.
  • The nav app is required. The EDS header block no longer builds a nav of its own. If App Builder is unavailable, both delivery paths show an empty header; production use would need a fallback (for example a cached copy of the last good nav).
  • Nav changes usually appear within 5 minutes, and within 15 minutes at worst. The nav HTML is cached for 5 minutes and may be served stale for up to 10 more while it refreshes (max-age=300, stale-while-revalidate=600). Pages assembled by the edge function are cached no longer than the nav. Page content changes in EDS are purged as usual.
  • Only the Stage workspace is deployed. A Production workspace exists in the App Builder project but has no deployment pipeline yet.
  • The nav on its own page (?format=page) uses system fonts; inside the site it uses the site's fonts.

Deploying

Nav app (App Builder)

  • Deployed automatically to the Stage workspace by a GitHub Actions workflow on every change to nav-app/ on main. It runs the tests, deploys an optimized build, and checks the live action returns the nav.
  • One-time setup: an App Builder project in Adobe Developer Console, an OAuth Server-to-Server credential on the workspace, and the workspace values stored as GitHub secrets (npm run ci:secrets). See nav-app/README.md.
  • Manual deploy: npm run deploy in nav-app/.

Edge function (AEM Edge Functions)

  • Needed first: a Cloud Manager program (sandbox or production) with the Edge Delivery Services add-on; this site onboarded in its Edge Delivery tab; a custom domain with an SSL certificate and DNS pointed at the Adobe-managed CDN (required even for testing); and the Deployment Manager role.
  • Then: set the domain in edge-nav/config/cdn.yaml, run aio aem edge-functions setup, deploy edge-nav/config with a Cloud Manager Edge Delivery pipeline, and deploy the function with aio aem edge-functions build and npm run deploy.
  • Full steps: edge-nav/README.md.

Running behind Akamai

Walgreens serves its site through Akamai. The nav app and the EDS header block work the same behind any CDN, so nothing in the nav itself changes. The decision is where the nav is inserted into the page, and therefore which CDN runs the edge logic:

OptionHow it worksWhat it needsTrade-offs
A · Akamai EdgeWorker Akamai serves EDS directly, as in Adobe's standard Akamai setup for EDS. An EdgeWorker (responseProvider with html-rewriter) fetches the page and the nav fragment, adds the nav to <header> and streams the result. Akamai EdgeWorkers. A path on the Walgreens Akamai property that routes to the App Builder nav app (for example /nav-fragment), because EdgeWorker sub-requests must go to Akamai-served hostnames. A port of the insertion logic from edge-nav/src/stitch.js, which has no Fastly dependencies. One CDN, no extra hop, and it fits an existing Akamai operation. The AEM Edge Function isn't used; the same logic runs on Akamai instead. EdgeWorker CPU, memory and sub-request limits depend on the resource tier.
B · Akamai in front of the Adobe-managed CDN Akamai forwards page requests to the Adobe-managed CDN, where the edge-nav edge function inserts the nav, as built in this prototype. Everything in Deploying for the edge function, plus Akamai configured to forward to the Adobe CDN with the site's host (X-Forwarded-Host) and an authentication key. Reuses the edge function unchanged, but two CDNs sit in series: one more network hop and two caches to keep in step on purges. Adobe documents a customer CDN in front of its CDN for AEM publish; confirm with Adobe that this topology is supported for EDS sites with Edge Functions before choosing it.
C · No edge logic Akamai serves EDS directly, and the header block fetches the nav in the browser. This is the path the prototype already uses on aem.page and aem.live. Nothing beyond Adobe's standard Akamai setup for EDS. Optionally, route the nav fragment through the Akamai property so Akamai caches it too. The simplest to run, but the nav appears after the page loads (the fragment request took about 0.3 s in testing). PageSpeed on this path scored 96 on mobile and 99 on desktop.

Applies to every option

  • Akamai to EDS: follow Adobe's Akamai setup for EDS. That means origin main--<repo>--<org>.aem.live; the request headers X-Forwarded-Host, X-BYO-CDN-Type: akamai and X-Push-Invalidation: enabled; honouring origin Cache-Control; and push invalidation, so EDS publishes purge Akamai.
  • Content Security Policy: in A and B the inserted nav's <script> tags must carry the page's per-response nonce, as edge-nav does today. In C the header block's scripts are allowed automatically.
  • Caching assembled pages: EDS asks for long CDN lifetimes and nav changes don't purge pages. Pages with the nav inserted should be cached no longer than the nav fragment (5 minutes in the prototype), as edge-nav does.
  • Fallback: if the nav fragment is slow or fails, return the page unchanged and let the header block load the nav in the browser.
  • Audience variants (locale, store, signed-in state) must be part of the fragment URL and of the cache key in whichever CDN does the insertion.

Implementation notes

Details that shaped the code and are worth knowing when extending it:

  1. Content Security Policy. EDS pages allow only scripts carrying a per-response nonce ('strict-dynamic'). The edge function copies each page's nonce onto the nav's script tags; without it, the browser would block the nav's JavaScript.
  2. Cache lifetimes. EDS asks the CDN to keep pages for up to 2 days, and nav changes don't purge pages. The edge function therefore caps assembled pages at the nav's 5-minute lifetime, and fallback pages at 60 seconds so assembly is retried soon.
  3. Layout stability. When the nav is loaded in the browser, its stylesheet must apply before the markup is inserted; otherwise the unstyled nav briefly lays out tall and shifts the page.
  4. App Builder build output. The deployed index.html is minified (attribute quotes removed) and asset names are content-hashed, so the action reads them from the deployed file rather than hard-coding them.
  5. Production builds. Deploys use NODE_ENV=production with --web-optimize; a plain aio app deploy ships React's unminified development build (about 1.2 MB).
  6. Bundler setup. The browser bundle needs the process package installed, and package.json must not declare an engines.node field, which would make the bundler target Node instead of the browser.
