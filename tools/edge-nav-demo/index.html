Walgreens storefront · ancillary dev demo

Edge-stitched nav demo

The Walgreens site nav built as a server-rendered React app and delivered inside the first HTML response of the Edge Delivery Services (EDS) page. The browser gets the nav already rendered, instead of waiting for the header block to fetch /nav and build it client-side.

Decisions

DecisionWhy
Adobe-managed CDN + AEM Edge Functions for the stitching (Part 2) The demo should stay on the Adobe stack. Edge Functions are in beta and run on Fastly Compute under Adobe's CDN. For EDS sites, requests are routed to them with cdn.yaml rules and deployed through a Cloud Manager config pipeline plus aio aem edge-functions deploy.
App Builder hosts the nav app It also keeps the app on Adobe. A Runtime web action does the server render, and the same project's static hosting serves the browser bundle.
Plain React server rendering, not Next.js Runtime actions are short-lived OpenWhisk functions. Next.js expects its own long-running Node server, and there's no supported adapter. Bundling Next into an action would be fragile and add cold-start time and package-size problems that have nothing to do with what the demo proves. renderToString + hydrateRoot shows the same server-render-then-hydrate pattern.
htm tagged templates instead of JSX The same component file runs in Node (the action and tests), webpack (aio's action bundle) and Parcel (aio's web bundle) with no transpile step, in keeping with the project's no-build approach.
The nav reads the authored /nav document Authors keep editing /nav exactly as they do for the EDS header block. parse-nav.js uses the same slot order as blocks/header/header.js.
Port the EDS header block, rather than re-scraping walgreens.com The block is already the project's port of walgreens.com. Nav.js renders the same DOM and classes, and nav.css is header.css scoped to .wnav with the brand tokens it needs, so the site and the app stay one design.
Store and account render in both rows; CSS shows one The EDS block moves them between rows with JavaScript when the viewport changes. A server render can't know the viewport, so the app renders both and toggles them at the 768px breakpoint.
The browser bundle loads as a classic <script defer> On the EDS page, the bundle comes from another origin, and App Builder static hosting sends no CORS headers. Module scripts need CORS and classic scripts don't. aio's Parcel build already emits a classic script, and the action copies whatever tag the deployed index.html has.
Commerce drop-ins left out Search submits a plain GET /search?q=, the account panel shows the signed-out "Sign in" button, and the cart is a plain link. They aren't needed to prove the delivery pattern.

Deployment

CI (normal path)

.github/workflows/deploy-nav-app.yaml runs on every push to main that touches nav-app/, and on demand from the Actions tab. It runs:

  1. npm ci and npm test
  2. OAuth server-to-server sign-in with adobe/aio-apps-action
  3. NODE_ENV=production aio app deploy --web-optimize --no-publish, from nav-app/
  4. A smoke check that the deployed action returns the nav markup and its <script>

It deploys to the stage GitHub environment. Until that environment has its secrets, the job skips with a notice instead of failing.

By hand

Run npm run deploy from a linked nav-app/ folder. It's the same optimized build as CI.

One-time setup (done for Stage)

  1. Create an App Builder project in Developer Console.
  2. Add I/O Management API → OAuth Server-to-Server to the Stage workspace.
  3. Run aio app use --merge.
  4. Run npm run ci:secrets (use -- --check to list what it found first).

The "Deploy from GitHub Actions" section of nav-app/README.md has the details.

Gotchas found along the way

These shaped the code. Each is fixed, and most have a test or a CI check guarding it.

  1. process polyfill. Parcel needs the process package to bundle React for the browser, and aio's Parcel run doesn't auto-install it. Fix: process is a devDependency.
  2. engines.node in package.json. Parcel reads it as "build for Node" and left React out of the browser bundle as an external module. Fix: no engines field.
  3. aio emits a classic script, not a module. The action originally looked only for type="module", so the fragment shipped with no JS. Fix: copy whatever script tag index.html has. That turned out to be required anyway, since static hosting sends no CORS headers.
  4. A plain aio app deploy doesn't minify and ships React's development build. Fix: npm run deploy and CI use NODE_ENV=production … --web-optimize.
  5. --web-optimize also minifies index.html and drops attribute quotes (<script src=/web-src.9485b3f2.js defer>). The quote-only parser found neither asset, and the CI smoke check caught it. Fix: src/assets.js accepts quoted and unquoted values, with tests using the exact deployed HTML.
  6. .env keys containing -. aio names the OAuth context after the credential (AIO_ims_contexts_Credential__in__Walgreens__Nav__-__Stage_…), and the secrets helper's parser skipped those keys. Fix: keys are read up to =, with a test.
  7. Files aio leaves behind. The downloaded workspace JSON (it can hold credentials), .aws.tmp.creds.json and web-src/src/config.json are gitignored in nav-app/.gitignore.
  8. React attribute names. htm passes attributes straight to React, so templates must use className. class renders, but React's development build warns about it.

Known limitations

  • Fonts on the standalone page. ?format=page shows system fonts, because aem.page doesn't send CORS headers for fonts. Injected into the EDS page, the site's Inter and Source Sans Pro apply.
  • Commerce features aren't wired: no product-discovery popover, no signed-in account state, no mini-cart or cart count.
  • Only Stage is deployed. A Production workspace exists in the project but has no CI job yet.
  • Content is up to 5 minutes stale. An author's change to /nav shows up once the action's cached response expires; the stale-while-revalidate window is another 10 minutes.

Part 2 hand-off

What Part 1 already provides

  • A ready-to-inject fragment at one stable URL. It's self-contained: stylesheet, markup, model and script in one response.
  • CORS on the action (Access-Control-Allow-Origin: *) and a cacheable response (max-age=300).
  • A script that loads from another origin without CORS (classic defer), so the stitched page needs no extra headers.
  • A smoke-checked deploy on every merge, so the fragment URL stays healthy.

What Part 2 needs

  • Access to a Cloud Manager program with an EDS site on the Adobe-managed CDN, where cdn.yaml and the edge function are deployed. Check this before starting.
  • An aem.cdn-scoped credential for the aio aem edge-functions commands.
  • Two design calls: which pages get the stitched nav, and what to do when the fragment fetch fails or is slow (fall back to the EDS header block's client-side render).
  • Coexisting with the EDS header block. On stitched pages the block must not render a second nav. Either the edge function drops the block, or the block skips itself when #wnav-root is already present.
